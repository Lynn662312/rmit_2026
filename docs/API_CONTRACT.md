## 0. Core principles

1. **Browser-side TideCloak encryption:** Encrypt the entire incident report with the real TideCloak SDK before any API call. Never POST plaintext, title, incident category, identity, or evidence metadata.
2. **Backend stores ciphertext only as report content:** Backend must not have a decryption API and never decrypt. A valid nonempty string alone does not prove real encryption; verification requires actual SDK integration/testing.
3. **Real server-side authentication:** Every route requires a TideCloak **access token** verified on the server with the SDK's real verifier and actual starter configuration. Header: `Authorization: Bearer <access-token>`. Never trust `role`, `userId`, or `ownerSub` supplied by a browser, nor decode an unverified JWT as authentication.
4. **Ownership:** Internally save the authenticated token's verified `sub` as `ownerSub` when creating a report. Use it for ownership checks. **Never return `ownerSub` or any other reporter identifier in API responses.** This metadata is not anonymous to the server operator; do not claim full reporter anonymity.
5. **Read visibility:** A reporter may list/view their own reports. An *investigator* may list/view all reports **only if the backend verifies the configured investigator role from the real token**. A school admin with no such role cannot list other users' reports. Member A must verify the actual role claim mapping (e.g. a committed `_tide_report.selfdecrypt` role if it is used for investigator access). A client `canDecrypt` flag is **not** sufficient for API authorization.
6. **Write ownership:** Only the original reporter (`verified sub === stored ownerSub`) may PATCH or DELETE their report. An investigator can read permitted reports, but may not edit/delete someone else's submission. If the server cannot enforce ownership, PATCH/DELETE must fail closed (not return success).
7. **Demo-only persistence:** In-memory, server-side `Map`; restart, rebuild, or multiple server instances can lose or isolate reports. Use single-process local dev for the demo. Use synthetic data only.
8. **Error consistency:** JSON errors have `{ "error": "message" }`. Do not include private data, tokens, stack traces or plaintext in errors/logs.

## 1. Record schemas (fixed)

### Internal, server-only data

```js
{
  id: 'r_f6d...',               // server-generated opaque identifier
  createdAt: '2026-10-22T06:00:00.000Z',
  ciphertext: '<opaque-serialized-Tide-payload>',
  ownerSub: '<VERIFIED TOKEN sub>' // internal ONLY; never included in API JSON
}
```

### Public API report

```json
{
  "id": "r_f6d...",
  "createdAt": "2026-10-22T06:00:00.000Z",
  "ciphertext": "<opaque-serialized-Tide-payload>"
}
```

- `id`: opaque string generated by the backend. Clients cannot choose or overwrite it.
- `createdAt`: UTC ISO-8601 string generated on the backend. Immutable.
- `ciphertext`: non-empty string representing a losslessly serialized Tide encrypted payload. The backend treats it as opaque; only the real TideCloak browser SDK can attempt decryption.
- Maximum request body: **64 KiB** (65,536 UTF-8 bytes); oversized POST/PATCH returns **413**. Content-Type must be `application/json`.
- Do not add plaintext fields (`title`, `description`, `reporterName`, etc.) to this API.

## 2. API endpoints — FROZEN

| Method | Path | Request JSON | Success JSON | Status |
|---|---|---|---|---|
| POST | `/api/reports` | `{ "ciphertext": "..." }` | `{ "id": "...", "createdAt": "..." }` | **201** |
| GET | `/api/reports` | none | `{ "reports": [PublicReport, ...] }` | **200** |
| GET | `/api/reports/:id` | none | `{ "report": PublicReport }` | **200** |
| PATCH | `/api/reports/:id` | `{ "ciphertext": "..." }` | `{ "report": PublicReport }` | **200** |
| DELETE | `/api/reports/:id` | none | **No body** | **204** |

### 2.1 POST `/api/reports` — Create

```http
POST /api/reports
Authorization: Bearer <valid-TideCloak-access-token>
Content-Type: application/json

{"ciphertext":"<opaque-serialized-Tide-payload>"}
```

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id":"r_123","createdAt":"2026-10-22T06:00:00.000Z"}
```

- Extract internal `ownerSub` **only** from server-verified claims.
- Reject missing/empty/nonstring `ciphertext`, malformed JSON, extra fields, and oversized bodies; never store on failure.
- You do not need an explicit reporter `userId` field.

### 2.2 GET `/api/reports` — List

```http
GET /api/reports
Authorization: Bearer <valid-TideCloak-access-token>
```

```json
{
  "reports": [
    {"id":"r_123","createdAt":"2026-10-22T06:00:00.000Z","ciphertext":"<opaque-serialized-Tide-payload>"}
  ]
}
```

- Reporter: returns only reports with `ownerSub` equal to the verified `sub`.
- Investigator: returns all reports **only** with a server-verified, agreed investigator role claim.
- Other authenticated user: returns only their own reports (usually empty).
- Return an empty `reports` array rather than leaking other users' records. Do not return `ownerSub`.

### 2.3 GET `/api/reports/:id` — Read one

```json
{"report":{"id":"r_123","createdAt":"2026-10-22T06:00:00.000Z","ciphertext":"<opaque-serialized-Tide-payload>"}}
```

- Allowed for owner or server-verified investigator.
- Missing report or inaccessible report: **404** to prevent probing for other users' report IDs.
- Bad ID format: **400**.

### 2.4 PATCH `/api/reports/:id` — Replace ciphertext

```http
PATCH /api/reports/r_123
Authorization: Bearer <valid-TideCloak-access-token>
Content-Type: application/json

{"ciphertext":"<new-opaque-serialized-Tide-payload>"}
```

```json
{"report":{"id":"r_123","createdAt":"2026-10-22T06:00:00.000Z","ciphertext":"<new-opaque-serialized-Tide-payload>"}}
```

- **Owner-only.** Do not permit edits merely because someone is an investigator/admin.
- `id` and `createdAt` remain unchanged. No plaintext passes through the API.
- Backend cannot confirm the new ciphertext is actually valid Tide ciphertext without Tide-aware validation; UI must encrypt first, and real E2EE must be tested independently.
- If authenticated investigator can view this report but is not its owner, return **403**. For an unrelated non-owner without view access, return **404**.
- If real server-side identity/ownership verification is unavailable, reject the operation; **never** allow unrestricted updates.

### 2.5 DELETE `/api/reports/:id` — Remove

```http
DELETE /api/reports/r_123
Authorization: Bearer <valid-TideCloak-access-token>
```

```http
HTTP/1.1 204 No Content
```

- **Owner-only.** Do not accept client-supplied `userId`, `isOwner`, etc. No request body.
- If authenticated investigator can view but does not own report, return **403**. For a different user without read permission, return **404**.
- Missing/previously deleted report returns **404** (not idempotent success in this team's contract).
- The 204 response **must be empty**; frontend must not attempt `response.json()`.
- Hard delete is for this synthetic-data hackathon demo only; a real institutional reporting system needs evidence retention, audit policies and legal review.

## 3. Error contract

| Code | Meaning | When |
|---|---|---|
| **400** | Bad Request | Malformed JSON, wrong fields/types, invalid id, unsupported content-type |
| **401** | Unauthorized | Missing, expired or invalid Tide access token |
| **403** | Forbidden | Valid token, insufficient permission for a known/viewable operation (e.g. investigator attempting PATCH of someone else's report) |
| **404** | Not Found | Missing record OR a record hidden from this user |
| **413** | Payload Too Large | POST/PATCH body exceeds 64 KiB |
| **500** | Internal Server Error | Unexpected server failure; do not leak internal details |
| **503** | Service Unavailable | Optional: real Tide verifier/config unavailable; **fail closed**, never silently bypass authentication |

Error JSON for all applicable non-204 responses:

```json
{"error":"Short safe error message"}
```

No body for successful DELETE (204). Use `Cache-Control: no-store` on report responses because they contain confidential ciphertext and IDs.

## 4. Frozen frontend API client contract

**Location:** `features/api/reportsClient.js` (Member C owns implementation; Member B uses it).  
**Export:** `makeReportsClient(token)`. `token` is the real Tide access token supplied by Member A's security adapter. No hardcoded tokens.

```js
const api = makeReportsClient(security.token);

await api.createReport(ciphertext);
// => { id, createdAt }

await api.listReports();
// => [{ id, createdAt, ciphertext }, ...]

await api.getReport(id);
// => { id, createdAt, ciphertext }

await api.updateReport(id, newCiphertext);
// => { id, createdAt, ciphertext }

await api.deleteReport(id);
// => undefined (after a successful HTTP 204)
```

- `listReports()` returns the **array** (unwrap `{reports: []}` internally) to preserve Member B's original UI contract.
- `getReport()` and `updateReport()` return the **report object** (unwrap `{report: ...}` internally).
- `createReport()` returns the small creation result, unchanged from the original guide.
- `deleteReport()` handles 204 without JSON parsing.
- Non-2xx calls throw an `Error` with an appropriate user-safe message; no silent mock/fallback.
- For POST/PATCH, caller **first** invokes `security.encryptReport(plaintext)` then passes only ciphertext to this client.
- Existing B UI can continue using just `createReport` and `listReports` immediately. The other three client functions can exist unused until UI features are added.

## 6. Minimum tests and integration gates

### Backend tests Member C can run without A/B

- [ ] POST with missing/invalid token returns 401 when real verification is available (otherwise explicitly report BLOCKED; never implement fake production auth).
- [ ] Invalid JSON / missing or extra body keys: 400; oversized POST/PATCH: 413.
- [ ] Pure storage test: create, list, read by id, replace ciphertext, delete; no plaintext metadata.
- [ ] Authenticated owner can GET/PATCH/DELETE their record.
- [ ] Different subject cannot read, update or delete another reporter's record.
- [ ] Investigator can read all **only after** A confirms server-verifiable role mapping; cannot update/delete others' reports.
- [ ] DELETE returns 204 with **zero** body bytes; following GET returns 404.
- [ ] Return payloads never include `ownerSub`, token, real name, email or user ID.
- [ ] No API route directly decrypts ciphertext or logs sensitive content.

### UI + API can integrate as soon as B and C are ready

- [ ] B uses `makeReportsClient(token)` and the frozen methods/response shapes.
- [ ] B can preview against **clearly labeled mocks** if real login is not ready. Do not claim this as real security.
- [ ] Integration with A is needed to run real authentication, encrypted submission, investigator read and unauthorized decryption denial.
- [ ] **Critical security gate:** Student A ciphertext → Investigator B decryption has been **actually tested**, not presumed from role assignment.

## 7. Change control

- **Frozen externally:** endpoint paths/methods, JSON shapes, client method names/signatures, error code meanings, body limit, ownership rules.
- **Allowed without notifying other roles:** internal functions, Map implementation, module internals, error logging without secrets, code formatting, testing organization.
- **Coordinate with B and A before changing:** auth header or SDK integration, role claim mapping, API client signatures, response shapes, routes. If the Tide SDK makes a frozen item unworkable, **document the blocker; do not silently change it**.
- **No server-side plaintext crypto endpoints** and no real personal incidents. This project is a hackathon demo, not a deployable incident-management product.
